# Flexible Layouts

* * *

## Summary

A "flexible layout" lets editors build a single post's page from a list of section
blocks. They pick each section's type, fill in its content, and drag the sections into
order. The site still uses one [single template](Single%20Templates.md) for the whole post
type. Use it when posts of one CPT share a frame (hero, CTA) but the middle of the page
genuinely varies from post to post. This was first built on `connected-by-fusion-sftp`'s
Service pages, after the designer confirmed the services carry very different amounts of
content and couldn't share one fixed template.

If every post has the same sections, use an ordinary single template with fields
connected to each section instead. A flexible layout is more work for the editor and for
us, so only use it where the content really varies.

## Prior art

- **Creative Clique (Toolset Views)**: portfolio items have a `feature-sections`
  repeating field group with a "Content Type" select plus every field any type might need.
  A Toolset View (`Portfolio Feature Sections`) lists the current post's items, ordered by
  `toolset-post-sortorder`, and uses `[wpv-conditional]` blocks to pick markup per type. It
  sits in the `Single Portfolio Item` Themer layout as a single module. Fine for a handful
  of near-identical types, but every type's markup lives in one View.
- **Coastal Kitchen family (ACF, no BB)**: ACF Flexible Content, rendered with
  `get_template_part( 'template-parts/flexible/' . get_row_layout() )` inside a section
  wrapper that owns background and spacing. We copy this one-file-per-type structure, not
  the data model, because Toolset has no equivalent of ACF Flexible Content.

## Data model (Toolset Types)

Toolset doesn't let one repeater hold different field sets per item. Instead, use **one
repeating field group** whose fields cover every section type, and switch on a type
select:

```
<cpt>                              e.g. service
└── <cpt>-section                  RFG: one item per page section
    ├── Section Type   (select, required, first field)
    ├── Background     (select: white / grey …)
    ├── <type>-specific fields     each with conditional display on Section Type
    ├── <cpt>-section-<thing>      nested RFG for a type that has its own repeating items
    └── …
```

- **Section Type** select comes first. Its option values are the **component folder
  names** (`image-content-row`, `testimonial-quote`, …), so the renderer can dispatch on
  the value directly.
- **Type-specific fields** are prefixed with the section slug and an abbreviation of the
  type (`service-section-icr-heading`), because Types field slugs are global across the
  site. Each one gets **conditional display** on the type select, so editors only see the
  fields for the type they picked. This works inside a repeating group; CC's
  `feature-sections` already does it. Stored format, in the field's
  `data.conditional_display`:

  ```php
  array(
      'relation'   => 'OR',
      'conditions' => array(
          'condition_<md5>-1' => array( 'field' => '<type-select-slug>', 'operation' => '=', 'value' => 'image-content-row' ),
      ),
      'custom'     => '',
      'custom_use' => '0',
  )
  ```

- **Types that repeat items of their own** (a features grid, a slider's slides) use a
  **nested repeating group** inside the section group, rather than a fixed number of
  slots. Its relationship has the section CPT as the parent type. Types (checked on
  3.6.3) has **no conditional display for a repeating group**, only for fields inside one
  and for whole post field groups. So label the nested group with the type it's for, e.g.
  "Features (Features / Benefits sections only)", and, if editors need it hidden, use the
  small admin script described under
  [Hiding nested groups by section type](#hiding-nested-groups-by-section-type).
- **Keep repeating group slugs to 20 characters or fewer.** Each one is a real post
  type, and WordPress rejects longer post type names. Registration appears to succeed,
  but inserting an item fails with "Could not insert post into the database". On CBF,
  `service-section-feature` became `section-feature` for this reason. Field slugs aren't
  limited this way.
- **Background** is per section, because a BB row background can't be set per item when
  all sections render from one module (see below).

The registration wiring (slug matching, `hidden` status, `_repeatable_group_<id>`,
`toolset-post-sortorder`) is in
[Toolset → Repeating field groups](../General/Toolset.md#repeating-field-groups-are-relationships-in-disguise).

## Rendering: reuse the existing section components

Don't copy each section's markup into a View or loop. The section types should be the
same `view-template/` components already used on hand-built pages, so a section looks the
same whether it was dropped onto a layout or generated by the loop.

This works because the BDVS plugin renders a theme component through plain functions
defined in the `bdvs-content-template` module's `frontend.php`:
`process_theme_template_content( $html, $settings )` fills `{{attribute}}` placeholders
and `[bdvs_bt_form_repeater]` blocks from a settings object, and
`enqueue_template_style()` / `enqueue_template_script()` load the component's assets. A
theme helper can call the same functions with field values in place of module settings
(`cbf_render_component( $slug, $atts )` on `connected-by-fusion-sftp`).

The pieces:

1. **`view/<cpt>-sections` component.** `view.php` builds `$query` from the current
   post's section item IDs, sorted by `toolset-post-sortorder`, with `orderby => post__in`.
   `template.php`'s loop item outputs the section wrapper and calls the renderer.
2. **A per-type mapping function** (`cbf_render_service_section( $section_id )`). It
   switches on the Section Type, reads that type's Types fields (and nested group items),
   and maps them onto the component's attribute names before calling
   `cbf_render_component()`. Adding a section type means adding the select option, its
   fields, and one `case` here. The component itself doesn't change.
3. **One module in the Themer layout.** Fixed parts of the page (hero, CTA, anything
   every post shows) stay as ordinary rows. The variable middle becomes a single row
   holding the sections module.

Gotchas when mapping fields onto component attributes:

- **Every attribute the template references must be passed**, using `''` for empty
  ones. The plugin only replaces placeholders whose keys exist, so a missing key leaves a
  literal `{{name}}` in the page. The same applies to each item in a form-repeater array.
- **Images:** Types image fields store a URL. Components built for BB `photo`
  attributes usually expect an attachment ID (`[bdvs_bt_image_url item='…']`). Either use
  the component's URL mode if it has one (`image-content-row`'s `use-image-url`), or
  convert with `attachment_url_to_postid()`.
- **WYSIWYG fields:** pass them through `wpautop()` so they arrive paragraph-wrapped,
  the same as a BB editor attribute does.
- **Component JS must be instance-scoped.** A script that finds its parts with
  `.closest('.fl-module-content')` breaks once several instances share one module. Scope
  to the component's own outer element instead (`heading-slider` was changed this way).
- The plugin's helper functions only exist once a `bdvs-content-template` module has
  started rendering. Call the renderer from a `view/` component's `template.php`, not from
  arbitrary hooks.

## Fields shared across section types

When most types need the same kinds of content (a heading, some text, an image, a
button), give them **shared fields** instead of a set per type: one
`<group>-heading`, one `<group>-text`, and so on. The field's conditional display lists
every type that uses it, with `relation: OR`, and its label says what it's for in each
type (e.g. "Text (Problem, Motivation: body; Testimonial: quote)"). On CBF's SEO
sections this kept 13 section types down to 11 fields. Only add a type-specific field
where the content genuinely means something different.

Note that Types (3.4.11+) **clears a conditionally hidden field's value when the post is
saved**. Changing a section's type and saving loses the fields the new type doesn't use.

## Hiding nested groups by section type

Because Types can't conditionally show a nested repeating group, CBF uses a small admin
script (`js/admin.js`, enqueued only on the CPT's edit screen by
`cbf_admin_enqueue_scripts()`):

- PHP builds a map of nested group **slug → (type field slug, types that use it)**, turns
  the slugs into group post IDs, and passes it to the script with
  `wp_localize_script()`.
- The script finds each nested list's control (`.c-rgx__nested--control`), reads the
  parent item through Types' knockout model (`ko.dataFor( el )`, which gives
  `repeatableGroup.id` and `item.id`), and reads that item's type select, named
  `types-repeatable-group[<item ID>][<type field slug>]`.
- It hides the list's title and toggle when the type doesn't use it. An open list is
  closed through Types first (`repeatableGroup.toggleGroupVisibility()`), so Types' own
  count of open lists stays right.
- It re-runs on type change, and on a `MutationObserver` over `#poststuff`, because Types
  draws and adds items after page load.

The horizontal view (a per-user Types option) only lets the script hide the cell's
control, not the whole column.

## More than one template on the same CPT

A CPT can have a second flexible layout, e.g. a new design that each post is moved to
when its new content is ready, without touching the posts still on the old one. CBF's
Service CPT has **Standard** and **SEO** templates this way.

- **A Page Template select** on the CPT (`service-page-template`: `standard` / `seo`).
  Empty means the original template. Pin existing posts to the original value
  explicitly: if the select's default is the new template, an existing post with no
  saved value would switch the next time it's saved.
- **A separate repeating group per template** (`service-section` and `seo-section`), not
  new types in the old one, so a post's new sections can be written and previewed while
  its live page still shows the old template.
- **One field group per template, with a group-level condition** on the select (Types
  group conditional display, e.g. *SEO Page* shown when `service-page-template = seo`).
  Types evaluates group conditions live in the editor, so changing the select swaps the
  groups without saving. A hidden group's values and repeating group items are kept. A
  repeating group sits in whichever field group holds it, so the original template's
  group had to move out of the shared *Service Fields* group into its own group to be
  hidden.
- **Two published Themer layouts** for the same location (`post:<cpt>`), and a filter on
  `fl_theme_builder_current_page_layouts` that removes the one not wanted for the
  current post. Find the layouts by slug, not ID. **Deploy the filter before publishing
  the second layout**, or every post briefly matches both. Deleting the second layout on
  its own puts every post back on the original.
- **Preview:** CBF's filter honours `?cbf-template=seo|standard` for users who can edit
  the post, and ignores it for everyone else.

## Pre-filling new posts

New posts can start with a full set of sections, filled with placeholder content, for
editors to rewrite, reorder or delete:

- Hook `wp_insert_post` for a **new** post of the CPT (`$update` false). This fires when
  "Add New" opens, so the sections are there on the first edit screen.
- Create each item as a post of the section type, set `toolset-post-sortorder`, and link it
  with `toolset_connect_posts( '<group slug>', $parent_id, $item_id )`. Nested items are
  linked the same way to their section.
- Make the seeder **skip posts that already have sections**, so it never overwrites and
  can be run again safely, e.g. once over existing posts with `wp eval`.
- `toolset_get_related_posts()` **finds nothing under an auto-draft parent**, though
  Types' own repeater loader (`Types_Field_Group_Repeatable_Mapper_Legacy`, which the edit
  screen uses) does. The edit screen still shows the seeded items. It's just that code
  checking "already seeded?" through the relationship API won't see them until the post is
  saved.
- Placeholder images and files: upload one of each to the Media Library once, store the
  IDs in an option, and reuse them.

## Clean up items when a post is deleted

Types **leaves repeating group items behind** when their parent post is deleted. With
seeding, every abandoned "Add New" leaves a full set of orphans when WordPress cleans up
auto-drafts after a week. Hook `before_delete_post`, find the post's items with Types'
loader (`do_action( 'toolset_do_m2m_full_init' )` first, so it works from cron too), and
delete nested items, then sections. See `cbf_delete_seo_sections()`.

## A `view/` component as a section

A section can also be an existing `view/` component (CBF's Case Study section reuses
`view/case-study`). `cbf_render_view_component( $slug, $context_post_id )` does what the
module would: it sets the parent post as the current post, includes `view.php` for
`$query`, enqueues the component's assets, outputs `template.php` with the part between the
BDVS LOOP markers repeated per post, then restores the outer post. It returns `''` when
the query is empty, so the section can be left out instead of showing "No items found".

## Section wrapper, background and spacing

Because all sections render from **one** module, BB's own row settings can't give each
section its background, vertical padding and centring. This is the legitimate
"component owns its full-bleed layout" exception in the root `CLAUDE.md`. The row
holding the module is set to **Width: Full, Content Width: Full**, with zero padding and
zero module margins, and each section outputs:

```html
<section class="cbf-service-section cbf-service-section-<type> cbf-service-section-bg-<bg>">  <!-- background + vertical padding -->
  <div class="fl-row-fixed-width fl-row-content">                                            <!-- centring at the site row width only -->
    <div class="cbf-service-section-inner">                                                  <!-- side gutter only -->
      …component markup…
    </div>
  </div>
</section>
```

The width cap and the padding sit on separate elements, as the root `CLAUDE.md` requires.
The side gutter matches what module margins give a hand-built row (20px on
`connected-by-fusion-sftp`). **Vertical padding is set per section type**, copied from the
`padding_top`/`padding_bottom` of the hand-built row each type replaces, so a converted
page keeps its existing spacing exactly. Don't swap in one generic value: on CBF that
visibly changed the rhythm and was rejected. Where two types used to share one row
(CBF's heading slider directly above a features block), a sibling rule removes the
padding between them: `:has(+ …)` on the first, `+` on the second.

|-------|-------|

| Themer layout | `Service Single` (ID 11): hero row → sections row → case study row → CTA row |
